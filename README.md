# Barcode Document Sorter

Приложение автоматически сортирует сканы документов по штрихкодам. Оно следит
за сетевой папкой, распознаёт штрихкоды в PDF и изображениях, ищет фамилию в
локальной базе SQLite и **копирует** документ в папку с фамилией. Документы, для
которых не нашлось соответствия или штрихкод не распознан, попадают в служебные
папки. Все действия видны в веб-интерфейсе на русском языке.

Главный приоритет проекта — **абсолютная сохранность исходных документов**:
приложение не удаляет, не перемещает, не переименовывает и не изменяет файлы в
исходной папке и не создаёт там никаких служебных файлов. Исходная директория
монтируется в контейнер в режиме `read-only`, а приложение дополнительно
проверяет на старте, что выходные и служебные каталоги не пересекаются с входным.

Актуальные результаты тестирования и проверки Docker-образа: [`TEST_REPORT.md`](TEST_REPORT.md).

## 1. Возможности

- Периодическое сканирование исходной папки с вложенными директориями.
- По умолчанию обрабатываются только файлы, изменённые за последние
  `PROCESS_FILES_NEWER_THAN_HOURS` часов (24); `0` отключает фильтр.
- Поддержка форматов: **PDF, JPG, JPEG, PNG, TIFF, TIF**.
- Распознавание штрихкодов: Code 128, Code 39, Code 93, EAN-13, EAN-8,
  UPC-A, UPC-E, QR Code, Data Matrix, PDF417, ITF, Codabar, Aztec
  (список настраивается).
- PDF: штрихкоды ищутся **на всех страницах** (с ограничением `MAX_PDF_PAGES`
  и настройкой `PDF_DPI`).
- Несколько штрихкодов на странице и в документе.
- Предварительная обработка изображений: поворот, повышение контраста,
  бинаризация, увеличение мелких штрихкодов.
- Проверка «стабильности» файла: документ не обрабатывается, пока сканер
  дописывает его по сети.
- SQLite: таблицы `barcode_mappings`, `documents`, `processing_logs`;
  WAL, `busy_timeout`, повторные попытки при блокировке.
- Веб-интерфейс: статистика, последние операции, управление сканером,
  CRUD базы штрихкодов, импорт/экспорт CSV, журналы с фильтрами и пагинацией.
- Авторизация, CSRF-защита, ограничение попыток входа, security-заголовки.
- Ретраи с экспоненциальной задержкой и ограничением попыток.
- Восстановление состояния после перезапуска контейнера.
- Один контейнер, без микросервисов и без Docker socket.

## 2. Как приложение защищает исходную папку

| Уровень | Механизм |
|---|---|
| Docker | Том `${INPUT_DIR}:/app/input:ro` монтируется только для чтения |
| Docker Compose | `read_only: true` для корневой ФС, `cap_drop: ALL`, `no-new-privileges` |
| Приложение | Никакой код не открывает файлы в `INPUT_DIR` на запись |
| Приложение | На старте проверяется, что `OUTPUT_DIR`, `DATA_DIR`, `LOG_DIR` не находятся внутри `INPUT_DIR` и наоборот |
| Приложение | Если путь не находится под `INPUT_DIR` — обработка запрещена |
| Приложение | Символические ссылки в `INPUT_DIR` игнорируются; выходные директории-ссылки запрещены |
| Копирование | Запись только во временный файл внутри `OUTPUT_DIR`, затем атомарная публикация |
| Проверка | На старте выполняется диагностика режима `read-only` исходной директории |
| Тесты | Тесты снимают хеши/размеры/mtime всего дерева `INPUT_DIR` до и после обработки и проверяют, что оно не изменилось; отдельный тест работает при `chmod 0555` |

Приложение **копирует** документы. Слов «переместить» или «удалить» в рабочем
коде обработки нет.

## 3. Архитектура

```
barcode-sorter/
├── app/
│   ├── main.py                     # FastAPI-фабрика, lifespan, middleware
│   ├── config.py                   # настройки из переменных окружения
│   ├── database.py                 # SQLAlchemy/SQLite, WAL, ретраи
│   ├── security.py                 # пароли, CSRF, rate limit, session secret
│   ├── deps.py                     # зависимости FastAPI
│   ├── templating.py               # Jinja2 + фильтры
│   ├── healthcheck.py              # healthcheck контейнера
│   ├── cli.py                      # python -m app.cli hash-password
│   ├── logging_config.py
│   ├── models/                     # barcode.py, processing.py
│   ├── routers/                    # auth.py, dashboard.py, barcodes.py, logs.py
│   ├── services/
│   │   ├── scanner.py              # периодическое сканирование
│   │   ├── barcode_reader.py       # ZXing-C++ / PyMuPDF / Pillow
│   │   ├── document_processor.py   # хеш, поиск, копирование, статусы
│   │   ├── file_copier.py          # безопасная запись в OUTPUT_DIR
│   │   ├── csv_service.py          # импорт/экспорт CSV
│   │   ├── stats.py
│   │   ├── safety.py               # диагностика read-only input
│   │   └── validation.py
│   ├── templates/                  # Jinja2 (русский UI)
│   └── static/                     # Bootstrap 5 + HTMX (локально)
├── tests/                          # pytest
├── data/                           # SQLite и session secret (том)
├── logs/                           # файловые логи (том)
├── Dockerfile
├── docker-compose.yml
├── .env.example
├── requirements.txt
├── requirements-dev.txt
└── README.md
```

Поток обработки одного документа:

1. Сканер находит поддерживаемый файл и проверяет, что размер и `mtime` не
   меняются `FILE_STABILITY_CHECKS` раз подряд.
2. Вычисляется SHA-256 и размер/`mtime` файла. Если такой документ уже
   успешно обработан — он пропускается.
3. Из документа извлекаются все штрихкоды.
4. Выполняется точный поиск по `barcode_mappings`.
5. Определяется статус и папка назначения.
6. Резервируется уникальный путь в SQLite, затем документ копируется во
   временный файл внутри выходной директории и атомарно публикуется.
7. В `documents` и `processing_logs` записывается результат.

## 4. Статусы обработки

| Статус | Папка | Значение |
|---|---|---|
| `sorted` | `Иванов/` | Штрихкод найден в базе |
| `unmatched` | `UNMATCHED/` | Штрихкод распознан, но не найден в базе |
| `unreadable` | `UNREADABLE/` | Штрихкод не обнаружен |
| `needs_review` | `NEEDS_REVIEW/` | В документе штрихкоды разных фамилий |
| `error` | — | Ошибка чтения/копирования; будут повторные попытки |
| `pending` | — | Документ в очереди |
| `processing` | — | Документ обрабатывается прямо сейчас |

## 5. Требования к серверу

- Ubuntu Server 22.04/24.04 или другой Linux с Docker.
- 2 CPU и 2 ГБ ОЗУ как разумный минимум (распознавание PDF — CPU-bound).
- Свободное место под `OUTPUT_DIR` и `DATA_DIR`.
- Docker Engine 24+ и Docker Compose v2.
- Установленный сетевой ресурс SMB/CIFS или NFS, смонтированный на хосте.
- **`DATA_DIR` должен находиться на локальном диске.** SQLite не следует
  размещать на SMB/NFS: блокировки по сети работают ненадёжно и можно потерять
  данные. Выходной каталог может быть сетевым.

## 7. Подключение сетевой папки

### SMB/CIFS (Ubuntu)

```bash
sudo apt install -y cifs-utils
sudo mkdir -p /mnt/network/scans

# Файл с учётными данными (не попадает в git и compose)
sudo tee /etc/cifs-scans.credentials > /dev/null <<'EOF'
username=scanuser
password=СЕКРЕТ
domain=WORKGROUP
EOF
sudo chmod 600 /etc/cifs-scans.credentials

# /etc/fstab
//fileserver/scans /mnt/network/scans cifs \
  credentials=/etc/cifs-scans.credentials,ro,uid=1000,gid=1000,\
iocharset=utf8,vers=3.1.1,nofail,_netdev 0 0

sudo mount -a
ls -la /mnt/network/scans
```

Флаг `ro` на уровне ОС — дополнительная защита: даже в случае ошибки
приложение не сможет ничего записать в источник. Изменения, которые сканер
пишет со своей стороны, всё равно видны: `ro` запрещает запись только с этого
сервера.

### NFS

```bash
sudo apt install -y nfs-common
sudo mkdir -p /mnt/network/scans
# /etc/fstab
fileserver:/export/scans /mnt/network/scans nfs4 \
  ro,hard,timeo=600,retrans=2,nofail,_netdev 0 0
sudo mount -a
```

Проверьте, что файл доступен на чтение пользователю, под которым работает
приложение (UID 1000 по умолчанию):

```bash
sudo -u '#1000' head -c 32 /mnt/network/scans/любой_скан.pdf | xxd | head -1
```

## 8. Подготовка каталогов

Приложение в контейнере запускается под непривилегированным пользователем
`app` с UID/GID `1000`. Каталоги, которые оно должно записывать, принадлежать
этому UID:

```bash
sudo mkdir -p /mnt/documents/sorted
sudo chown -R 1000:1000 /mnt/documents/sorted
sudo chmod 750 /mnt/documents/sorted

cd /opt/barcode-sorter        # каталог с проектом
mkdir -p data logs
sudo chown -R 1000:1000 data logs
chmod 700 data
chmod 750 logs
```

Если UID 1000 занят другим сервисом, пересоберите образ со своими UID/GID:

```bash
APP_UID=1500 APP_GID=1500 docker compose build
```

и выставьте владельца каталогов соответственно `1500:1500`.

## 9. Настройка `.env`

```bash
cd /opt/barcode-sorter
cp .env.example .env
chmod 600 .env
nano .env
```

Минимум, что нужно изменить:

```dotenv
INPUT_DIR=/mnt/network/scans
OUTPUT_DIR=/mnt/documents/sorted
DATA_DIR=./data
LOG_DIR=./logs
WEB_PASSWORD=СГЕНЕРИРУЙТЕ_НАДЁЖНЫЙ_ПАРОЛЬ
TZ=Europe/Moscow
```

Сгенерировать пароль:

```bash
openssl rand -base64 32
```

### Пароль в виде хеша (необязательно, но безопаснее)

Чтобы не хранить пароль открытым текстом в `.env`, посчитайте
PBKDF2-хеш и укажите `WEB_PASSWORD_HASH` вместо `WEB_PASSWORD`:

```bash
# локально, без Docker
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python -m app.cli hash-password

# либо после сборки образа
docker compose run --rm --no-deps --entrypoint python \
  barcode-sorter -m app.cli hash-password
```

В `.env`:

```dotenv
# WEB_PASSWORD=...
WEB_PASSWORD_HASH='pbkdf2_sha256$600000$соль$хеш'
```

Хеш содержит символы `$`, поэтому заключайте значение в **одинарные кавычки**.
Уберите строку `WEB_PASSWORD=`, иначе пустое значение приведёт к понятной
ошибке конфигурации при старте.

### Сессионный секрет

Если `SESSION_SECRET` не задан, приложение создаёт файл
`DATA_DIR/.session_secret` с правами `0600`. При его потере все сессии
инвалидируются, данные при этом не страдают. Для неизменности сессий при
пересоздании контейнера можно задать `SESSION_SECRET` (32+ случайных байта).

## 10. Запуск

Проверьте конфигурацию и соберите образ:

```bash
cd /opt/barcode-sorter
docker compose config
docker compose build
docker compose up -d
docker compose ps
docker compose logs -f
```

Ожидаемый статус: `Up ... (healthy)`.

```bash
docker compose build      # пересобрать образ
docker compose up -d      # запустить/обновить контейнер
docker compose logs -f    # смотреть логи
docker compose restart    # перезапустить приложение
docker compose down       # остановить и удалить контейнер
```

**`docker compose down` не удаляет данные.** Все данные лежат в bind-mount
каталогах `INPUT_DIR`, `OUTPUT_DIR`, `DATA_DIR`, `LOG_DIR`. Приложение не
содержит ни одной команды автоматического удаления данных. Не удаляйте
каталоги `data/` и `output/` вручную, если хотите сохранить историю.

Остановить только на время работ:

```bash
docker compose stop
docker compose start
```

## 11. Веб-интерфейс и первичная настройка

Адрес по умолчанию: `http://<адрес-сервера>:8000/`.

1. Откройте страницу входа и введите `WEB_USERNAME` / `WEB_PASSWORD`.
2. На главной странице проверьте блок «Состояние сканера»:
   - исходная папка должна быть «доступна» и иметь статус `read-only`;
   - сканер — «Работает».
3. Перейдите в «База штрихкодов» и добавьте первое соответствие либо
   импортируйте CSV.
4. Положите тестовый скан с известным штрихкодом в `INPUT_DIR`.
5. В течение `SCAN_INTERVAL + FILE_STABILITY_CHECKS × FILE_STABILITY_INTERVAL`
   документ появится в статистике, а копия — в папке с фамилией.

Кнопки на главной:

- **Запустить полное сканирование** — немедленный проход (не создаёт
  параллельных обработчиков);
- **Приостановить / Возобновить** — управление автоматическим сканированием.

## 12. Импорт и экспорт CSV

Формат:

```csv
barcode,surname
4601234567890,Иванов
4601234567891,Петров
4601234567892,Сидоров
```

Правила импорта:

- кодировка UTF-8 (для совместимости принимается также Windows-1251 и BOM);
- обязателен заголовок `barcode,surname`;
- штрихкод хранится строкой, ведущие нули не теряются;
- дубликаты внутри файла и уже существующие штрихкоды пропускаются;
- строки с пустыми или недопустимыми значениями попадают в отчёт об ошибках;
- существующие записи не изменяются и не удаляются;
- по завершении показывается число добавленных, пропущенных и ошибочных строк.

Экспорт: кнопка «Экспорт CSV» на странице базы. Файл отдаётся в UTF-8 с BOM,
чтобы корректно открываться в Excel.

> Excel может автоматически преобразовать длинный числовой штрихкод. Перед
> импортом задайте колонке `barcode` текстовый формат.

## 13. Структура выходных директорий

```
OUTPUT_DIR/
├── Иванов/
│   ├── scan_001.pdf
│   └── scan_002.pdf
├── Петров/
│   └── scan_003.jpg
├── UNMATCHED/     # штрихкод распознан, но не найден в базе
├── UNREADABLE/    # штрихкод не распознан
└── NEEDS_REVIEW/  # разные фамилии в одном документе
```

- Документы всегда **копируются**, исходник остаётся на месте.
- При совпадении имени существующий файл не перезаписывается: новая копия
  получает имя `scan_1.pdf`, `scan_2.pdf` и т.д.
- Фамилия очищается от недопустимых символов; выход за пределы `OUTPUT_DIR`
  (path traversal) невозможен.
- Файлы публикуются атомарно: сначала временный файл, затем атомарная
  публикация без перезаписи.

## 14. Как работает сканер

- Используется **периодический обход директории**, а не inotify/watchdog:
  события на SMB/NFS приходят нестабильно.
- Интервал обхода — `SCAN_INTERVAL` секунд.
- По умолчанию обрабатываются только файлы, изменённые за последние
  `PROCESS_FILES_NEWER_THAN_HOURS` часов. Фильтр применяется **после** проверки
  дедупликации (путь + SHA-256), поэтому уже обработанные файлы не
  переобрабатываются. Для разового импорта всего архива задайте `0`.
- Перед обработкой файл должен `FILE_STABILITY_CHECKS` раз подряд иметь
  неизменные размер и время модификации; проверки разделены
  `FILE_STABILITY_INTERVAL` секунд. К окну свежести добавляется запас на
  проверку стабильности, чтобы файл не «выпал» из окна, пока дописывается.
- Одновременно может выполняться только один проход сканирования.
- Одновременно обрабатывается не более `MAX_FILE_WORKERS` документов.
- Успешно обработанные файлы пропускаются по паре «путь + SHA-256».
- Документы с незавершённой записью в БД (`pending`, `error`, `processing`)
  повторяются независимо от окна свежести: если контейнер простоял дольше
  суток, очередь не теряется и восстанавливается после запуска.
- Ошибки повторяются с экспоненциальной задержкой до `MAX_ATTEMPTS` раз
  (`RETRY_BASE_SECONDS`, `RETRY_MAX_SECONDS`).
- Если контейнер упал во время обработки, при запуске записи со статусом
  `processing` возвращаются в очередь (`STALE_PROCESSING_SECONDS`).
- Если исходная папка недоступна, приложение не падает, а повторяет попытки;
  веб-интерфейс продолжает работать.
- Приложение не удаляет и не перемещает файлы, а только читает их.

> **Ограничение окна свежести.** Если приложение остановлено дольше, чем
> `PROCESS_FILES_NEWER_THAN_HOURS`, файлы, появившиеся во время простоя и
> успевшие «постареть», при возобновлении не будут обработаны. Для разовой
> обработки таких файлов увеличьте окно или временно задайте `0`.
> Время берётся из `mtime` файла (время последнего изменения), а не из времени
> появления записи в каталоге.

## 16. Безопасность Docker

`docker-compose.yml` включает:

- `INPUT_DIR:/app/input:ro` — источник строго только для чтения;
- `read_only: true` — корневая ФС контейнера только для чтения;
- `tmpfs /tmp` — единственная временная область, с `noexec,nosuid,nodev`;
- `cap_drop: [ALL]` — все capabilities сняты;
- `security_opt: [no-new-privileges:true]`;
- `init: true`, `stop_grace_period: 45s` — корректная остановка;
- healthcheck через `GET /healthz`;
- ограничение размера json-log;
- отсутствие `privileged: true` и Docker socket;
- контейнер работает под непривилегированным UID 1000.

Проверить фактическое монтирование можно так:

```bash
docker inspect barcode-sorter --format '{{json .Mounts}}' | python3 -m json.tool
```

Внутри контейнера:

```bash
docker compose exec barcode-sorter mount | grep /app/input
# ожидаем ro
docker compose exec barcode-sorter sh -c 'touch /app/input/test' && echo BAD || echo 'input is read-only'
```

Если веб-интерфейс смотрит в интернет, поставьте reverse proxy (nginx/Caddy) с
HTTPS, задайте `WEB_BIND=127.0.0.1`, `SESSION_HTTPS_ONLY=true` и
`ALLOWED_HOSTS=scans.example.local`. Не публикуйте порт напрямую.

## 18. Резервное копирование и восстановление

### Резервная копия SQLite

Самый простой и надёжный способ — остановить приложение, чтобы SQLite
выполнил checkpoint WAL, и скопировать файл:

```bash
cd /opt/barcode-sorter
docker compose stop
cp data/barcode_sorter.db ~/backup/barcode_sorter-$(date +%F).db
docker compose start
```

Онлайн-копия без остановки (использует SQLite Backup API):

```bash
docker compose exec -T barcode-sorter python -c "\
import sqlite3; \
src = sqlite3.connect('/app/data/barcode_sorter.db'); \
dst = sqlite3.connect('/tmp/backup.db'); \
src.backup(dst); dst.close(); src.close()"
docker compose cp barcode-sorter:/tmp/backup.db ~/backup/barcode_sorter-online.db
```

Не открывайте `DATA_DIR/barcode_sorter.db` сторонними инструментами с хоста,
пока контейнер работает: в средах с виртуальными ФС это может привести к
конфликту WAL. Используйте остановку контейнера или команды внутри контейнера.

Резервируйте также `OUTPUT_DIR` (обычным копированием) и, при желании,
`DATA_DIR/.session_secret`.

### Восстановление

```bash
cd /opt/barcode-sorter
docker compose stop
cp ~/backup/barcode_sorter-2026-01-01.db data/barcode_sorter.db
rm -f data/barcode_sorter.db-wal data/barcode_sorter.db-shm
sudo chown 1000:1000 data/barcode_sorter.db
docker compose start
```

## 20. Восстановление после сбоя

1. Контейнер перезапускается политикой `restart: unless-stopped`.
2. При старте записи в статусе `processing` возвращаются в очередь.
3. Успешно обработанные документы пропускаются по «путь + SHA-256».
4. Путь копии сохраняется в БД **до** копирования; если контейнер упал после
   копирования, но до финальной записи, повторная обработка найдёт
   зарезервированный путь, сверит SHA-256 и переиспользует копию, а не создаст
   вторую.
5. Ошибки повторяются ограниченное число раз с растущей задержкой.
6. Данные SQLite и выходные файлы сохраняются между `restart`, `down` и
   повторным `up`, потому что лежат в bind-mount каталогах хоста.

## 22. Решение типичных проблем

**Контейнер перезапускается, в логах `unable to open database file`**
Проверьте права `DATA_DIR`: каталог должен принадлежать UID 1000 (`sudo chown
-R 1000:1000 data`), режим `700`.

**`ВНИМАНИЕ: INPUT_DIR доступна для записи`**
Папка примонтирована без `:ro` или хост-раздел не помечен read-only. Проверьте
`docker-compose.yml` и `mount`. Приложение всё равно не пишет в источник.

**Документы не появляются**
Проверьте «Состояние сканера»: папка доступна, сканер работает, нет ошибок.
Убедитесь, что расширение поддерживается, файл не начинается с точки и не
заканчивается на `.part`/`.tmp`. Обратите внимание на
`PROCESS_FILES_NEWER_THAN_HOURS`: по умолчанию файлы старше 24 часов
игнорируются. Также проверьте, что часы сканера/файлового сервера и сервера
приложения синхронизированы (NTP): фильтр сравнивает `mtime` файла с текущим
временем.

**Нужно обработать старый архив**
Временно установите `PROCESS_FILES_NEWER_THAN_HOURS=0`, выполните сканирование,
затем верните `24` и перезапустите контейнер (`docker compose up -d`).

**Штрихкод не распознаётся**
Увеличьте `PDF_DPI` (например, 300), проверьте качество скана, убедитесь, что
нужный формат есть в `BARCODE_FORMATS`. Такие документы попадают в
`UNREADABLE`.

**Штрихкод распознан, но документ в `UNMATCHED`**
Проверьте точное значение в базе (ведущие нули, пробелы). Поиск идёт по точному
совпадению строк.

**Документ в `NEEDS_REVIEW`**
В нём найдены штрихкоды разных фамилий. Перенесите вручную после проверки.

**`Errno 28` / «Недостаточно свободного места»**
Освободите место в `OUTPUT_DIR`; приложение повторит копирование.

**Healthcheck «unhealthy»**
`docker compose logs`, проверьте доступность `DATA_DIR`, затем
`docker compose exec barcode-sorter python -m app.healthcheck`.

**Неверное время в журналах**
Задайте `TZ` и перезапустите: `docker compose up -d`.

**Забыли пароль**
Измените `WEB_PASSWORD` (или `WEB_PASSWORD_HASH`) в `.env` и выполните
`docker compose up -d`.

**Ошибка при сборке на ARM64**
Используйте `zxing-cpp` 3.x — в `requirements.txt` уже указано `>=3.0,<4.0`,
для Linux ARM64 и x86_64 публикуются готовые wheel-пакеты.

## 23. Ограничения

- Рассчитано на **один экземпляр** приложения (один процесс uvicorn, один
  сканер). Не масштабируйте `docker compose up --scale` — это приведёт к
  конкуренции за SQLite и дублированию сканирования.
- SQLite подходит для умеренных объёмов (десятки тысяч записей и документов).
  Для очень больших нагрузок потребуется PostgreSQL.
- `DATA_DIR` нельзя размещать на SMB/NFS.
- Приложение не переименовывает и не удаляет исходные файлы; если нужно
  освобождать сетевую папку — делайте это отдельным регламентом на стороне
  сканера/администратора.
- Полнотекстовый поиск по содержимому документов не выполняется; хранится
  только штрихкод и метаданные.
